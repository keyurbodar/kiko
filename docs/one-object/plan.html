1. Architecture

Today every room and every agent is its own object. Each boundary between them needs a billed call, a stored queue, an alarm to drain it and a retry when it fails. The redesign removes the boundaries, so none of that is needed anymore.

2. One prompt, step by step

The human sends "find me a flight to Lisbon" to a room with one agent.

Before: ~140 rows, ~18 calls, ~6 alarms
  1. Room socket gets the message, stores it with FTS ~6 rows
  2. Burst row and a burst alarm are written 2 rows
  3. Burst alarm fires and calls AgentDO.receive 1 call
  4. Agent stores an inbox row, sets the heartbeat ~4 rows
  5. Heartbeat alarm opens pi-durable and runs 1 alarm
  6. Each step writes tasks, submissions and entries across 17 indexes ~100 rows
  7. Drafts go to the room every 300 ms, and the client ignores them ~6 calls
  8. Steps, typing and touch go to the room and UserDO ~8 calls
  9. Room stores the reply bubbles and FTS, then tells UserDO ~15 rows
  10. If any call fails, a 2 s retry runs forever ∞
After: ~6 rows, 0 calls, 1 alarm
  1. Owner socket gets the message and appends it to the room 1 row
  2. One setAlarm at the end of the burst window starts the run 1 row
  3. The alarm runs the agent: pi-durable on the journal store 0 rows
  4. Tokens, steps and typing go straight to the socket 0 rows
  5. Each finished model turn is one journal row ~3 rows
  6. The reply bubbles and search index are written once, in one transaction ~1–2 rows
  7. The chat list and unread count update in memory and are pushed to the socket 0 rows
  8. If it fails: one error bubble with a retry button, and nothing else 1 row

4. How it's built

New layout

apps/server/src/
  owner/
    owner-do.ts   the one Durable Object
    socket.ts     1 socket, hibernation, ping auto-reply
    clock.ts      the single alarm
    runs.ts       1 run = 1 invocation
    journal.ts    pi-durable Storage, 1 row/commit
    archive.ts    old history to R2
    after-run.ts  memory, naps, initiative
    schema.ts     ~15 tables
  room/   Room class: burst, members, log, search
  agent/  Agent class: factory, prompt, pacing
  user/   settings, keys, routines, recipes

The four mechanisms

Journal. pi-durable writes only through Storage.commit(writes). journal.ts wraps its MemoryStorage, applies the commit in memory, and appends the write list as one row to journal(seq PRIMARY KEY, data). On wake it loads the latest snapshot plus the rows after it. Past 500 rows it writes a new snapshot and drops the old rows.

Runs. runs.ts works out pending runs from messages an agent hasn't answered yet, so queuing a run writes nothing. Each run starts as its own invocation by calling the object's own stub, so every run gets its own 50 outgoing calls, 6 connections and 30 s of CPU. After 40 calls it saves and continues in a new invocation.

Clock. One alarm, set to the soonest due item: a queued run, the next routine, or a browser lease ending. Routines due in the same minute fire from one alarm and share awake time. Nothing is rescheduled after an error.

After a run. Memory capture, room summaries and initiative run once at the end of the human's run, in the same invocation, after the reply is sent. If one fails it waits for the next run.

5. What the human sees

Nothing about the experience gets worse. These all keep working exactly as today:

Paint from IndexedDB first, optimistic sends
Token streaming, steps panel, typing
Bursts: an agent reads several messages and answers once
Several agents in a room answering in parallel
Agents asking each other and handing off work
Background workers inside an agent
Routines that run while the browser is closed
Full-text search over all history
Extensions, Composio tools, the browser tool
A deploy mid-run resumes from the last finished turn

What changes: a failed run shows an error bubble with a retry button instead of the agent staying quiet or retrying in the background. Scrolling past about a month of history loads it from R2, which takes a moment the first time.

6. Plan: six PRs, each measured before it merges

Your data isn't carried over. PR 2 starts a fresh namespace and deletes the old classes. Every PR runs the overhead suite and has to reach its gate.

PR 1
Journal storage, and a run is one alarm

Add journal.ts and plug it into pi-durable inside today's AgentDO. Delete the heartbeat and retry backoff. Errors become bubbles. This alone stops what killed your account today.

gate: ≤ 40 rows per prompt, 0 alarms 1 min after a run, broken agent writes 1 row
PR 2
OwnerDO: one object, one socket

Move Room, Agent and User logic into plain classes inside OwnerDO. Delete mail, wake delivery, burst flush, signals, chat touch, the UserDO copies of rooms, FileDO, and the second client socket. New wrangler migration: delete 4 classes, add 1.

gate: 0 calls between objects, ≤ 15 rows per prompt, all model-free suites pass
PR 3
Background work rides on runs

Add after-run.ts and clock.ts. Delete the catalog sync timer, provider watch, memory-nap timers and the capture requeue. Routines due in the same minute share one alarm.

gate: idle 24 h = 0 alarms, 0 rows; 35 routines due in one minute = 1 alarm
PR 4
One schema

Merge the three schemas into about 15 tables on composite primary keys, without extra indexes. Search keeps FTS5 and is written once per reply.

gate: ≤ 8 rows per prompt, search suites pass
PR 5
Runs as their own invocations

Each run calls its own stub so it gets its own limits, and continues in a new invocation after 40 outgoing calls. Covers 20 agents running at once.

gate: 20 parallel fake runs of 60 tool calls each finish without a limit error
PR 6
R2 archive

Move history older than 30 days to R2 as compressed daily files and load it when the human scrolls up. Keeps the object under its 1 GB free limit.

gate: storage stays flat in a 90-day simulated run, scroll-back works

7. Risks and the answer to each

One object is a single threadRuns wait on the network, not the CPU. Your heaviest AgentDO call last week used 766 ms of CPU. One object handles about 1,000 requests a second; one human sends a few a minute.
128 MB of memory for 20 agentsAn agent's harness and extension sandbox load when it runs and load when it runs. When more than a few are loaded, the least recently used one is unloaded. The journal keeps memory small after a snapshot.
A bug in one agent affects all of themThat's also true today: they share one account and the same daily quota. Now one failure costs 1 row instead of the whole day.
A run longer than 15 minutesIt saves to the journal and continues in a new invocation, the same path as the 40-call limit.
A big rewritePR 1 is small and fixes today's outage on its own. Each later PR has a measured gate, and the model-free suites cover rooms, teams, routines and files.
