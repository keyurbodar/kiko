The idea in one line

Cloudflare bills rows, not transactions or bytes. A row can hold up to 2 MB, and each index on a table adds a row to every write. So the cheapest durable design writes one row at each moment that has to survive a crash, with no extra indexes, and derives everything else from those rows.

A simple chat has exactly two moments like that: your message is accepted, and the reply is done. The agent's own state adds one more. That's 3.

The 3 writes of a simple chat

1. Your messageOne message row, written before the ack. This row is also the agent's to-do: "unanswered messages" is a query over it, so no run ticket or pending row is needed.
2. The replyOne message row per bubble, written before "done". It marks the run as finished, so no separate run-ended row is needed.
3. The agent's statepi's six internal saves are batched into one journal row when the model turn completes. That keeps the run resumable without redoing a finished model call.

Longer runs

writes = 2 + model turns + outside actions

An outside action, such as sending an email or writing to an API, is saved before it runs, so a crash never repeats it. A three-turn run with no tools costs 5. With two tool actions it costs 7.

Going from 3 to 2, and why not 1

2 is a stretch goal. It means putting the agent's turn state inside the reply's row, so one row covers both "the reply is done" and "the run can resume". That turns the message table into the agent's log. It's possible, but it ties the room's history to pi's storage format, so we'll measure 3 first and only do this if it stays clean.

1 isn't possible without risking your data. Your message has to be saved before the ack, and the reply only exists seconds later. Those are two different moments, so they need two writes.
