### 1.4 How API-key auth is supplied per request
Three layers, highest precedence first (models.ts applyAuth ~835-868; ai/src/types.ts:136 `ProviderRequestOptions.apiKey`):
1. Explicit `options.apiKey` on `stream/complete/streamSimple` wins per field ("Explicit request options win per-field", models.ts:~855).
2. `options.env` (a `ProviderEnv` record) scopes provider config (Cloudflare account ids, Azure, Vertex, etc.) and is consulted before `process.env` (types.ts:142-145; ai/README.md:1711).
3. `Models.getAuth(providerOrModel, overrides)` (models.ts:737) resolves from the injected `CredentialStore` then ambient env via `AuthContext.env(name)`.
- Provider auth objects: `ProviderAuth { apiKey?: ApiKeyAuth; oauth?: OAuthAuth }` (ai/src/auth/types.ts:243-250). `ApiKeyAuth.resolve({ctx, credential, signal})` returns `{auth:{apiKey?, headers?, baseUrl?}, env?, source?}` (types.ts:150-170). Default env-var helper: `envApiKeyAuth(name, envVars)` (ai/src/auth/helpers.ts:10-33).
- Credential storage is app-owned: `CredentialStore { read, list, modify, delete }` (auth/types.ts:~57-97). `modify` is the only write path and must serialize per provider; Models runs OAuth refresh inside `modify` so concurrent requests cannot double-refresh (comment at auth/types.ts:~52-58, resolve.ts:107-138). Default is `InMemoryCredentialStore` (auth/credential-store.ts:4-). For kiko, implement `CredentialStore` over a DO's SQLite/KV with encryption. Stored shape: `Credential = ApiKeyCredential {type:"api_key", key?, env?} | OAuthCredential {type:"oauth", refresh, access, expires, ...extra}` (auth/types.ts:~17-37).
- Default `AuthContext` reads `process.env` and uses `node:fs` for fileExists, lazily and defensively; "env vars from process.env (undefined in browsers)" (auth/context.ts:20-35). It is injectable via `createModels({authContext})`, so on Workers pass `{env: async n => workerEnv[n], fileExists: async () => false}`.
- Agent-level hook: `AgentLoopConfig.getApiKey(provider)` is called before every LLM request (agent/src/types.ts, agent-loop.ts:401) for short-lived tokens.
- Browsers/Workers: ai/README.md:1629-1650 says to pass `apiKey` explicitly; Bedrock is Node-only (README:1650).

### 1.5 OAuth / subscription login flows
Shape: there are NOT separate `startLogin / exchangeCode / refreshToken` exports. Each provider exposes one `OAuthAuth` object (ai/src/auth/types.ts:~195-220) with:
- `login(interaction: ProviderAuthInteraction, options?): Promise<OAuthCredential>`
- `refresh(credential, signal): Promise<OAuthCredential>`
- `toAuth(credential): Promise<ModelAuth>`
plus `name`, `isSubscription?`, `loginLabel?`. Entry points on Models: `models.login(providerId, "oauth"|"api_key", interaction, options)` (models.ts:756-811) and `models.logout(providerId)` (models.ts:813). Refresh is invoked automatically via `resolveProviderAuth` (auth/resolve.ts:107-153; also models.ts:622).
Interaction is a callback object (auth/types.ts:~100-150): `interaction.prompt({type:"text"|"secret"|"select"|"manual_code", message, ...})` returns a string, and `interaction.notify({type:"auth_url"|"device_code"|"info"|"progress", ...})`. This is the seam for a web UI: the flow runs on the server, `notify(auth_url)` goes to the browser, the user pastes the code back via `prompt(manual_code)`.
The token exchange and refresh helpers inside each file are module-private (not exported): e.g. `exchangeAuthorizationCode` ai/src/auth/oauth/anthropic.ts:94, `refreshAnthropicToken` :231, `loginAnthropic` :138, `loginAnthropicCopyCode` :191. To call them individually you must copy/port the file.

Providers with OAuth (providers that register `oauth: lazyOAuth(...)`): anthropic (ai/src/providers/anthropic.ts:81), openai (ChatGPT sign-in, openai.ts:14), openai-codex (openai-codex.ts:13), github-copilot (github-copilot.ts:16), openrouter (openrouter.ts:17), kimi-coding, meta, xai, radius. Flow modules: ai/src/auth/oauth/{anthropic,openai-codex,openai-chatgpt,github-copilot,openrouter,kimi-coding,meta,xai,radius}.ts. Loader: ai/src/auth/oauth/load.ts (loaders for each; uses a bundler-opaque `import(variable)` so bundlers do not follow, load.ts:1-12).
**Google/Gemini: NOT FOUND.** No Google OAuth flow (google.ts and google-vertex.ts are API-key/ADC only; grep for gemini-cli/antigravity found nothing in src).

## 3. packages/codemode (@earendil-works/pi-codemode)

- Sandbox: **QuickJS compiled to WebAssembly** (`quickjs-wasi` 3.6.2, codemode/package.json) running inside a **Node `worker_threads` Worker**, fresh worker + fresh VM per `execute()` (README "How it works"; runtime/host.ts:1 `import { Worker } from "node:worker_threads"`, host.ts:76 `new Worker(options.workerUrl, {workerData})`; runtime/worker.ts imports `parentPort, workerData` from node:worker_threads). Host owns deadline (default 300000 ms, types.ts) and an interrupt flag (SharedArrayBuffer/Atomics, README "How it works", worker.ts:`interruptHandler: Atomics.load`), `memoryLimitBytes`.
- Host requirements: Node >= 22.19 (package.json engines); `node:worker_threads`, `node:fs/promises`, `node:module.createRequire` to find `quickjs-wasi/quickjs.wasm` (codemode/src/wasm.ts:1-35: `readFile` + `WebAssembly.compile(bytes)`); a worker entry URL (`workerUrl`). README:"Bundled hosts" documents overriding `wasm` and `workerUrl` for Bun compiled executables.
- **Works on Workers without containers? Not as shipped. UNVERIFIED but evident from code:** host.ts and worker.ts require `node:worker_threads` (Workers does not provide a general `Worker`), and wasm.ts uses runtime `WebAssembly.compile` from bytes, which Workers disallow (Workers only permit wasm imported as a precompiled module). Also `SharedArrayBuffer`/`Atomics.wait` interrupts are not available the same way. What IS portable and reusable: `source.ts` (options-line parser + Lark grammar `CODEMODE_SOURCE_GRAMMAR`), `declarations.ts` (TypeScript declaration renderer for tools; `renderDeclarations`, `MCP_TYPESCRIPT_PREAMBLE`), `identifier.ts`, `types.ts`, and `runtime/prelude-source.ts` (the JS prelude that runs inside QuickJS and builds `tools`, `store/load`, etc.). Whether quickjs-wasi itself runs on Workers: UNVERIFIED (package not installed).
  Alternative on Workers: Worker Loader/dynamic isolates is NOT used anywhere in this repo (grep "worker.loader|wrangler|durable object" over refs/pi excluding changelogs: only the durable README mention of running storage in DOs, durable/README.md:527).

## 4. packages/mcp (@earendil-works/pi-mcp)

Standalone client, no official SDK, no pi deps (mcp/README.md:3). Entry: mcp/src/index.ts. Exports: `.`, `./oauth`, `./testing` (package.json:8-24); `"sideEffects": false`.

Protocol `2025-11-25`, accepts 2025-06-18, 2025-03-26, 2024-11-05 (README "Supported protocol surface").
- Transports: `StdioTransport` (transports/stdio.ts, uses `node:child_process`, `node:process`), `StreamableHttpTransport` (transports/streamable-http.ts, fetch-only, injectable `fetch`), in-memory pair for tests. Streamable HTTP supports: POST with `accept: application/json, text/event-stream` (:226), SSE response streams, the server-to-client GET stream with reconnect, `Last-Event-ID` resumption (:358, 435-439), session DELETE (:265), session expiry error. **Legacy HTTP+SSE transport: not supported** (README: "legacy HTTP+SSE ... outside the initial core"; coding-agent/docs/mcp.md says the same).
- **Dynamic tool listing**: `listTools()` is on demand with cursor pagination. `tools/list_changed` is only delivered through the generic `onNotification` API, there is no automatic cache invalidation (README:"logging and tool-list-change notifications through the generic notification API").
- **Elicitation: NOT FOUND** in packages/mcp (no matches for "elicit" in src). coding-agent/test/mcp-conformance/README.md:41 says "pi does not support elicitation". Sampling, tasks, servers and JSON-RPC batches: also not supported (README last paragraph). Client capabilities advertised: roots only if configured (client.ts:216). A custom request handler can be added with `setRequestHandler("elicitation/create", ...)` plus advertising `capabilities.elicitation` through `McpClientOptions.capabilities` (client.ts:49) (UNVERIFIED that this works end to end; not tested).
- **OAuth for remote servers**: `@earendil-works/pi-mcp/oauth` (mcp/src/oauth/): protected-resource + authorization-server discovery (discovery.ts), PKCE auth-code flow, dynamic client registration, refresh with shared in-flight refresh, step-up auth for `insufficient_scope` (flow.ts; README OAuth section). Classes: `McpOAuthProvider` (provider.ts:43), `adaptOAuthProvider`, `authorizeMcp(oauth, {serverUrl, authorizationCode})`, `McpOAuthAuthorizationRequiredError`, `McpOAuthStateStore {load, save}` (provider.ts:15-18) which you implement for durable storage ("The package does not open a browser or choose where credentials are stored", README). `OAuthCallbackServer` (oauth/callback.ts:1 `import { createServer } from "node:http"`) is the only Node-only part and is optional: on Workers supply `redirectUrl` pointing at your own Worker route and call `authorizeMcp` with the `code` yourself. The transport takes `authProvider` (`AuthProvider`, auth-provider.ts), and bearer headers via `headers`.
- **Runs on Workers?** The client core, streamable-http transport and the OAuth flow use only fetch/Web APIs (the only `node:` imports in mcp/src are stdio.ts:1-2 and oauth/callback.ts:1). streamable-http.ts:203-206 explicitly calls `fetch` without a receiver because "Cloudflare Workers reject the platform fetch ('Illegal invocation')", with a regression test (mcp/test/streamable-http.test.ts:345, issue #10188). Strong evidence it was designed to run there; I did not run it (UNVERIFIED). Stdio cannot work on Workers. A long-lived GET SSE stream inside a DO is a design question (CPU/wall time), not an API gap.
- Helpers: `toLlmContent(result)` converts MCP content to pi-ai Text/Image content (protocol/content.ts). Wrapping MCP tools as AgentTools: README example. Coding-agent's integration: coding-agent/src/extensions/mcp/{runtime.ts,oauth.ts,index.ts}, config in `mcp.json` (docs/mcp.md).

### 5.1 Discovery
Directory scan rules (`loadSkillsFromDirInternal`, skills.ts:176-262):
- If a directory contains `SKILL.md`, it is a skill root; do not recurse further (skills.ts:199-224).
- Otherwise: recurse into subdirectories (skipping names starting with `.` and `node_modules`, :228-236); at the top-level directory only (`includeRootFiles=true`) direct `*.md` children are also loaded as standalone skills if they have a description (:255-265).
- `.gitignore`, `.ignore`, `.fdignore` are honored hierarchically (skills.ts:11, 57-70). Symlinks followed. Duplicate real paths silently skipped.
Locations, in priority order as assembled by `DefaultPackageManager` (package-manager.ts:2488-2565) (first name wins; later duplicates produce a `collision` diagnostic, skills.ts:~392-410):
1. Project `<cwd>/.pi/skills` (only if project trusted)
2. Project `.agents/skills` in cwd and each ancestor up to the git repo root (stops at the root where `.git` exists; if no git root, goes to filesystem root) (package-manager.ts:455-480; excludes `~/.agents/skills`), listed as project scope
3. User `~/.pi/agent/skills` (`getAgentDir()` = `$ENV_AGENT_DIR` or `~/.pi/agent`, config.ts:563-569; `CONFIG_DIR_NAME` `.pi`, config.ts:539)
4. User `~/.agents/skills`
Plus: settings.json `skills` arrays (global/project overrides, enable/disable), pi package `skills`, extension-provided skill paths, CLI `--skill` paths (resource-loader.ts:546-600). CLI paths come first in the merged list (resource-loader.ts:587-589). I did not read package-manager `addResource` ordering across dedupe; the exact final order when the same name appears in packages vs defaults is UNVERIFIED.

### 5.2 Frontmatter and validation
Parsed as YAML between a leading `---` and `\n---` (frontmatter.ts:12-28). Fields used by pi (`SkillFrontmatter`, skills.ts:74-78): `name`, `description`, `disable-model-invocation` (boolean). Other spec fields (license, compatibility, metadata, allowed-tools) are tolerated as `[key: string]: unknown`, not acted on (docs/skills.md "Write portable frontmatter").
- `name`: from frontmatter, else parent directory name (skills.ts:~327-329). Rules (validateName :97-117): <= 64 chars, regex `^[a-z0-9-]+$`, no leading/trailing hyphen, no `--`. Violations are warnings; the skill still loads (:330-337). Name need not equal the directory name (docs/skills.md).
- `description`: required, non-empty string, <= 1024 chars (validateDescription :122-132). Missing description means the skill is NOT loaded (:338-342); over-length is a warning.
- Malformed YAML in a `SKILL.md` produces a warning and no skill (:306-313). Non-`SKILL.md` standalone .md without a description are silently ignored (:319-321).
- Result `Skill {name, description, filePath, baseDir, sourceInfo, disableModelInvocation}` (skills.ts:80-87).

### 5.3 How skills appear in the system prompt
`formatSkillsForPrompt(skills, fileReadTool)` (skills.ts:~270-300): drops `disableModelInvocation` skills, then emits
```
The following skills provide specialized instructions for specific tasks.
Use the read tool to load a skill's file when the task matches its description.   (or "Use bash to load ...")
When a skill file references a relative path, resolve it against the skill directory (parent of SKILL.md / dirname of the path) and use that absolute path in tool commands.

<available_skills>
  <skill><name>..</name><description>..</description><location>/abs/path/SKILL.md</location></skill> ...
</available_skills>
```
All values XML-escaped (`escapeXml`). Only emitted when the agent has a `read` or `bash` tool (system-prompt.ts:165-168); the block becomes a named section `<skills>...</skills>` (system-prompt.ts:~178-182). Only name+description+path are in context.

### 5.4 On-demand loading
Two routes: (a) the model calls its `read` tool on the `<location>` path (nothing special on the server side; docs/skills.md "Understand how skills load"); (b) the user types `/skill:name args`, and `_expandSkillCommand` (agent-session.ts:2100-2121) reads the file, strips frontmatter, and replaces the text with `<skill name="..." location="...">\nReferences are relative to <baseDir>.\n\n<body>\n</skill>` followed by args. For kiko with no filesystem, expose a `load_skill(name)` tool that returns the body (and bundled references on demand) and change `<location>` to a skill id.

### 5.5 Prompt handling other than skills
- System prompt is built from named, independently replaceable sections (`buildSystemPromptSections`, system-prompt.ts:119-180): `preamble, tools, rules, docs, addendum, project_context, skills, cwd` + custom sections; each wrapped as `<name>\n...\n</name>`. The default preamble and `docs` section are coding-specific ("expert coding assistant", pi doc paths) and must be replaced for a general chat app (`customPrompt`, system-prompt.ts:~135-139). `diffSystemPromptSections` produces patches (system-prompt.ts:~200-215) used with transcript `SystemMessage.sections` (a pi-ai feature: system prompt and tool declarations are transcript system messages; see ai types `SystemMessage`).
- Prompt templates (`/name args`, `$1`/`$@` substitution): coding-agent/src/core/prompt-templates.ts (`loadPromptTemplates` :222, `expandPromptTemplate` :304, `substituteArgs` :71), docs/prompt-templates.md. Filesystem-based like skills.

## 7. packages/protocol, client, server

- **protocol** (protocol/): "Runtime-neutral routed envelopes, CBOR encoding, and byte-stream framing for the experimental Pi protocol", version 8 (protocol/src/protocol.ts:6 `PROTOCOL_VERSION = 8`). Messages: client `hello{version}`, `request{id,target,call}`, `cancel{id,target}`; server `hello{version,serverId}`, `hello_error`, `response{id, ok, result|error}`, `service_update{subscriptionId, update}`, `attachment{attachment: SessionTarget|null}` (protocol.ts:28-100). Targets: `{serverId}` or `{serverId, sessionId, attachmentId}`. Payloads (`call`, `result`, `update`) are opaque strict JSON; their grammar (`{serviceId, instance?, member, args}`, `$chord.service` control, subscriptions with snapshot + Delta updates) is owned by **@earendil-works/chord** (protocol/README.md). Framing: 4-byte big-endian length + one CBOR item (README), limits 16 MiB frame, 64 nesting. Dependencies: chord, typebox. No `node:` imports in protocol/src (grep clean). Explicitly "experimental and has no compatibility guarantees" (README last line).
- **client** (client/): `Client.connect({serverId, transportFactory})` where a `ByteTransportFactory` returns `{send(chunk), close()}` and calls `handlers.onData/onClose/onError` (client/README.md; client/src/transport.ts). Transport-neutral, the README example comment says "WebSocket, Unix socket, or another ordered byte transport". `client.request(target, call)`, `subscribeService()`, `createClientServiceTransport()` adapt to a Chord transport; typed APIs come from application-owned Chord service bindings. No automatic reconnect or replay (README). Only shipped transport: `@earendil-works/pi-client/unix` (client/src/unix.ts, node:net/node:fs). **A WebSocket transport is NOT FOUND** (grep of client/server/protocol src for WebSocket found only README prose; chord/PLANNING.md:407 lists WebSockets as a possible transport). Browser SDK for chat UI: NOT FOUND beyond this generic client + Chord. coding-agent re-exports the client (`coding-agent/src/client/index.ts`). The coding agent's own non-Node-API surfaces are the JSONL RPC mode over stdio (coding-agent/docs/rpc.md; src/modes/rpc/) and the SDK (docs/sdk.md); the RPC mode is a subprocess protocol, not a browser one.
- **server** (server/): "Experimental local server that routes clients to application-hosted durable Sessions" (server/README.md). `Server` + `ServerListener` abstraction (server/src/listener.ts) + routing (`session-router.ts`, `RoutedServerServiceHost`, `RoutedSessionHandle`, `SessionDirectory`, `SessionManagement`). Only listener shipped: Unix domain sockets (`server/src/transports/unix/listener.ts` uses node:net, node:fs/promises, node:crypto, node:path; exported `./unix`). `session-router.ts:1` imports `randomUUID` from `node:crypto` (trivial to swap for `crypto.randomUUID()`). The core router does not depend on pi-durable (package.json deps: chord, pi-protocol; no durable import in server/src: grep found only comments). It is designed around worker processes ("worker-local Session and Harness", "Neither an open JavaScript Session nor a Harness crosses the process boundary"), which maps loosely to one DO per session. In Workers you would write a WebSocket `ServerListener`/transport and bridge to a DO; whether the Server class itself is Workers-safe beyond `node:crypto`: UNVERIFIED (not read in full).
- **Peer authentication is explicitly not implemented**: "Peer authentication and authenticated service contexts are not implemented by the experimental transport" (protocol/README.md); "peer authentication remains application policy" (server/README.md). `ServerListener` doc: "Supplies established byte connections after any required transport authentication" (server/src/listener.ts:3), `ByteTransportFactory`: "fresh connected, authenticated transport" (client/src/transport.ts:17). So the auth hook is: authenticate in your WebSocket upgrade handler before handing bytes to pi-server.
- Alternative lighter path for kiko: skip pi-server/client and stream `AgentEvent`s from `Agent.subscribe` over your own WebSocket/SSE (AgentEvent is plain JSON-able). That avoids the experimental protocol. This is a design option, not something the repo provides.

## 8. End-user accounts, login, sessions: what "Pi handles BYOK, login, auth" actually means

Finding: pi has **no end-user account system**. All "login" and "auth" in the monorepo are **LLM-provider credential auth** for the single local user:
- "login" = `Models.login(providerId, "api_key"|"oauth", interaction)` (ai/src/models.ts:756) which prompts for an API key or runs a provider OAuth/device flow and stores a `Credential` in an app-supplied `CredentialStore` (ai/src/auth/types.ts). The coding agent's store is a local file `~/.pi/agent/auth.json` (0600, file-locked with proper-lockfile) (coding-agent/src/core/auth-storage.ts:1-60, 327-347).
- "auth" = resolving the per-request `apiKey`/headers/baseUrl (+refresh) for a model's provider (`Models.getAuth`).
- "BYOK" in this sense = the user's own provider API key or subscription token, per provider id, one credential per provider (CredentialStore "one credential per provider", auth/types.ts). Nothing is keyed per end user: a multi-tenant app must provide its own `CredentialStore` namespaced per user (e.g. one DO per user wrapping `CredentialStore`), plus its own account system.
- MCP OAuth (mcp/src/oauth) is the user authorizing pi against a remote MCP server; also not an account system.
- Server/client protocol: no authentication, no identity, no sessions-per-user (protocol/README.md, server/README.md). The only "session" concept is a conversation (`sessionId`, durable Session), not a login session.
- NOT FOUND: user registration, passwords, cookies/JWT, sign-in with Google/GitHub for the app itself, per-user quotas/billing, encryption-at-rest for credentials (auth.json is plain JSON with file mode 0600).
- Security consequence: ai/README.md:1642 warns that browser-held API keys are dangerous; production apps should keep keys server-side. For kiko: user accounts, per-user credential encryption, and WebSocket auth all must be built outside pi; pi supplies the `CredentialStore` seam and OAuth flow code (with the Node-only parts listed in 1.5).
- Also note the Claude/ChatGPT/Copilot "subscription" logins (`isSubscription: true`) reuse the first-party CLI client ids hard-coded in the flows (anthropic.ts:13, openai-codex.ts:~28, github-copilot.ts:~12 base64). Whether those providers permit use by a third-party hosted web app is a policy question not answered by this repo.
