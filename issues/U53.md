# U53 Prove "status" does not touch running work

**Model** Claude Haiku 5.5 medium. **Wave** 6. **Timebox** 75 min. **Port** 8853.

## Why

The owner's rule: while a worker runs, a human "what is the status" is answered by the lead from worker state and must not steer, stop, or restart the worker. A note meant for the work reaches the worker only through `steer_work`. This needs a deterministic proof with fake agents (AGENTS.md: team and loop behavior is tested with fake agents first, no tokens).

Read: `apps/server/src/agent/dev-fake.ts`, `apps/cli/src/verify/suites/workers.ts`, `mid-run.ts`, `core/agent/src/mid-run.ts`, `core/agent/src/workers.ts`.

## Do

Extend `apps/cli/src/verify/suites/workers.ts` (or the closest fake-agent suite) with a case:
1. The human asks for slow work; the fake lead calls `start_work`; the fake worker runs several slow steps.
2. Mid-work the human sends "what is the status?". Assert: the lead replies; its reply input contained the worker's live state; the worker conversation received no new input; the worker was not aborted or restarted; the worker finishes and its report reaches the human.
3. Then the human sends a note; the fake lead calls `steer_work`; assert the worker received exactly that input once.

If the fake agent cannot script `start_work` or `steer_work`, extend `dev-fake.ts` minimally. If the assertion reveals the rule is broken, stop and report with the evidence (STATUS blocked, QUESTION) rather than changing product behavior.

## Acceptance

- Run the suite on your own server: `bun yuki verify workers --url http://localhost:8853`, paste the result. Show it fails when you temporarily make the lead's status reply steer the worker (revert after).
- `bun scripts/check.ts` green after merging `main`.

## Report

**Result:** the rule holds. A human "what is the status?" mid-run is answered by the lead from the worker's live state, and the worker's input does not change. A note sent with `steer_work` reaches the worker once. No product code changed.

**Added case** `status does not touch the worker` in `apps/cli/src/verify/suites/workers.ts`:
1. The human asks for `[steps 8] find flights`. The lead calls `start_work`. The worker runs 8 slow steps.
2. Mid-run the human sends "what is the status?". The test waits for a `status:` bubble, checks it shows `w1 (running)`, checks w1 is still `running`, and checks w1's `submissionId` did not change.
3. Mid-run the human sends a note through `steer_work`. The test checks the report is exactly `report w1 done: work done: heard=[steps 8] find flights | only morning flights`. That string proves the status question never reached the worker and the note arrived once. It also checks there is one report.

**Fake lead** (`apps/server/src/agent/dev-fake.ts`): a status question now gets `status:` plus the `your workers:` lines from the raw input. The note is inside `<context>`, which `textOf` strips, so `rawOf` is used. This is the minimal extension the brief allowed.

**Order choice:** the brief's step 3 says "then" after the report. I sent the note while the worker still ran. A note after the report would re-run a finished worker, which tests a different path. This is a test-ordering choice, not a product choice.

**Failing on purpose (required):** I temporarily made the fake lead's status reply also call `steer_work` with the question. Output:
```
fail workers
status does not touch the worker: w1's input after the status answer differs (- expected, + actual)
- 20
+ 37
```
The submission id moved from 20 to 37, so the worker received the status question. The mutation was then reverted. `git diff` shows only the status echo. Note this mutates the fake lead, not product code. It tests that the suite catches a lead that steers.

**Dev server incident:** my first mutation run failed in the first case with `timed out waiting for the worker's report`. The server log showed `Reloading local server` twice. Wrangler's hot reload resets Durable Objects and drops a running worker. I restarted my own server (PID tree only) and reran. The rerun showed the expected failure above. Lesson: edit the fake before starting a server, or restart after each edit.
