# Standing orders

Every worker reads this file in full before any work. AGENTS.md at the repo root overrides anything here.

You can ask the coordinator. If you reach a real design fork that you cannot settle by reading code or running something cheap, stop, commit any safe partial work, and end with `STATUS: blocked` and a `QUESTION` section that states the fork, the options, and your recommendation. The coordinator answers and starts your next round with your branch intact. Do not guess on a fork that changes behavior a user sees.

1. Read `AGENTS.md` first. Its non-negotiables and "ways to hurt yourself" are hard rules.
2. Work only inside the worktree path named in your brief. Run every command there (`cd <worktree> && ...`) and use absolute paths. Never edit files under `/home/keyur/kiko` itself, which is the coordinator's checkout of `main`.
3. Never run `pkill` or `killall`. Always pass `--url http://localhost:<your port>` (or set `YUKI_URL`) to every `bun yuki` command; the default port 8787 belongs to another session. If you start `wrangler dev`, pick a free port (`--port <n>` from your brief), record its PID, and stop only that PID before you finish.
4. Never rebase, reset another branch, push, or force anything. You may run `git merge main` into your own branch to pick up new checks from `main`; resolve only conflicts inside your scope, otherwise stop and ask. Commit on your own branch only. The coordinator lands branches on `main`.
5. Write only the paths in your brief's SCOPE, plus your own issue file `issues/<ID>.md` (removed automatically when the unit lands; git history keeps it), where you append a `## Report` section and, if you found anything the plan should know, a `## Discoveries` section. Never edit `issues/PLAN.md`, `issues/ledger.tsv`, `issues/decisions.tsv`, `issues/STANDING.md`, or another unit's issue file.
6. Reproduce before you fix. Every behavior change ships with a test that fails on the old code and passes on the new code. Say in your report that you saw it fail, with the output line.
7. Make the smallest change that fully solves the problem. Add an abstraction only when it deletes more than it adds. No speculative guards, options, or flags. Delete what your change makes dead.
8. Follow the surrounding code's idiom. The repo uses Effect v4 where it already uses Effect. Do not introduce Effect into plain code, and do not strip it from code that uses it.
9. Verify in proportion to risk. Lint only backend paths: `bunx biome check apps/server core apps/cli scripts` (the frontend has known lint errors outside this program). Always: `bun run typecheck` for the packages you touched, the test files that cover your change, and `bun scripts/check-imports.ts`. Run a `bun yuki verify <suite>` only when your change alters behavior that suite covers. Before you report, merge `main` into your branch and run `bun scripts/check-rules.ts` and `bun scripts/check-exports.ts`; landing fails on either. Do not run the full `bun scripts/check.ts` gate; the coordinator runs it once at landing.
10. The machine has 4 CPUs. At most two heavy commands run at once across every unit. Wrap each typecheck, test run, dev server, and `bun yuki verify` in `issues/bin/heavy.sh` from the main checkout, for example `/home/keyur/kiko/issues/bin/heavy.sh bun run --cwd apps/server test -- room-receive`. It waits for a free slot. Never run two heavy commands in parallel yourself. A dev server and the suite that drives it share one slot: run them in one call, `heavy.sh sh -c 'bun run --cwd apps/server dev --port <n> & pid=$!; sleep 20; bun yuki verify <suite> --url http://localhost:<n>; s=$?; kill $pid; exit $s'`. Thinking, reading and editing need no slot. Run heavy commands in the foreground with a long timeout and read their result in the same turn; a backgrounded job whose notice never arrives leaves you waiting on nothing.
10. Server tests: `bun run --cwd apps/server test -- <file-substring>` runs selected files, one workerd per file. Do not run the whole server suite unless your brief asks; the machine has 4 CPUs shared by many workers. If a test times out or shows a workerd broken pipe, check `uptime`; under heavy load rerun that one file once, and report a load-caused failure as such instead of chasing it.
11. Comments only for a non-obvious why. Interface strings are sentence case. No long dashes in docs or comments.
12. Never print, log, or commit a key. Dev keys live in `apps/server/.dev.vars` (a symlink); load them with `set -a; . apps/server/.dev.vars; set +a` when a model suite needs them.
13. No new dependency unless the brief allows it.
14. Commit message: plain sentences that say what changed and why. End with the line `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. One unit may be several commits; leave the branch clean (`git status --short` empty). Commit working steps early as `wip:` commits; a host restart kills agents mid-run and uncommitted work may be lost.
15. Timebox. When your brief's timebox expires, commit what works, mark what does not in your report, and stop.
16. Final message is your report, in this shape: `STATUS` (done, partial, blocked), `QUESTION` (only when blocked), `BRANCH`, `HEAD` (full SHA), `CHANGED` (files, one line each), `VERIFIED` (each command you ran and its result line), `FAILED-BEFORE` (the test that failed on old code), `DEVIATIONS`, `FOLLOW-UPS`.
