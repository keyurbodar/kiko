# U52 A human never has to resend a message

**Model** Claude Haiku 5.5 medium. **Wave** 6. **Timebox** 75 min. **Port** 8852.

## Why

The owner's rule: a human message is never dropped and never needs resending. Known edges:
- The socket drops a text frame over `MAX_TEXT = 16_000` characters (`apps/server/src/room/socket.ts:27`, `:66`). Find what the human sees then, and whether the client composer stops it first.
- The agent inbox refuses an entry over 128 KB as `too_large` (`core/agent/src/inbox.ts:66`), and `REFUSED.human` (`apps/server/src/room/receive.ts`) tells the human to send a shorter one. Bursts are split at `MAX_DELIVERY_BYTES` (`apps/server/src/room/burst.ts:34`). Decide from code and a test whether a human message can reach `too_large` at all.
- `full` (500 open entries) is retried by the room: confirm it is retried without human action.

## Do

1. List every path where a human message can fail to reach the agent, with file:line and how it is reached. Write it in your report.
2. Fix each reachable one at the right edge, so nothing asks the human to resend. The expected fix for long text: the client turns a paste or message over the limit into an attached text file, the way the composer already sends files (`apps/web-solid/src/composer/`), and the message carries the file. Keep the composer instant and optimistic (AGENTS.md). If a server path is unreachable from a human, prove it with a test and delete the dead human branch rather than keep a notice no one can trigger. Keep the agent row of `REFUSED`.
3. Interface strings are sentence case.

## Acceptance

- A test that fails on old code for each fixed path.
- If you touched the client: `bun run --cwd apps/web-solid test` and typecheck, and one real-browser check with the `verify-yuki` skill (`.cursor/skills/`) that a 20,000 character paste sends as a file and the agent receives it. Your own vite port and your own server on 8852.
- `bun scripts/check.ts` green after merging `main`.

PATHS WHERE A HUMAN MESSAGE CAN FAIL TO REACH THE AGENT
1. Text over 16,000 characters. `apps/server/src/room/socket.ts` `parse` returns null for `send` (line 66), `handleFrame` closes the socket with 1008. The client had no limit, so the message stayed in the outbox, was resent on every reconnect, and never arrived. Reached by pasting 16,001 or more characters. FIXED on the client.
2. Edit over 16,000 characters. Same close, `socket.ts:68`. FIXED: the composer refuses the edit with a toast.
3. Raw frame over 64 KiB. `socket.ts` `MAX_FRAME` (line 22). JSON escapes control characters into up to six characters, so 16,000 control characters make a frame of about 96 KiB, and the socket closes. NOT FIXED. Rare in practice. Follow-up.
4. Over today's reply limit. `apps/server/src/room/burst-flush.ts` `!turn.ok` branch calls `burst.delivered`, so the message is dropped. It shows the notice "they come back at HH:MM utc". Any human past the limit is affected. NOT FIXED. See QUESTION 2.
5. Inbox refuses too large. `core/agent/src/inbox.ts:66` counts envelope bytes plus brief bytes against 128 KiB. `apps/server/src/room/receive.ts` `REFUSED.human` posts the notice, then the burst drops the message. REACHABLE: a board of 200 open tasks owned by one agent with 200-character CJK titles gives a brief of about 124 KiB, and any 16,000-character message then goes over. Test: `human-delivery.test.ts` "a human message the board's largest brief rides with is refused as too large" passes on the current code, so it documents the path rather than a fixed one. NOT FIXED. See QUESTION 1.
6. Inbox full (500 open rows). `burst-flush.ts` `full` branch calls `burst.retry(DELIVERY_RETRY_MS)`, 2 seconds. CONFIRMED retried without human action: test "a burst the agent's inbox is full for stays pending and comes back without the human" passes, and no notice is posted. Caveat: it retries for as long as the agent takes no entries. Nothing gives up.
7. No chat row, or no recipient. `burst-flush.ts` `!chat` calls `burst.clear()`, and a burst with no recipient is marked delivered and dropped silently. I found no human path to either: the chat row exists while the room exists, and `resolveRecipients` falls back to the lead. UNVERIFIED that a lead is always present. Not fixed.
8. A send refused for an attachment that expired. `apps/server/src/room/pending.ts:134` refuses "attachment not found (removed or expired)", and `PENDING_TTL_MS` is 24 hours (`pending.ts:6`). The client marks the send failed (`room-store.ts:687`) and never resends it, so the human must re-attach and send again. Reachable when a draft sits a day before it is sent. NOT FIXED. Follow-up.
