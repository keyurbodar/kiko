# U91: RoomDO reads and writes

## Report

STATUS: done

Measured rows read and written per user and agent action in RoomDO, at a fresh size (4 human messages, 2 agent bubbles, 3 files) and at history (1,000 human messages, 1,000 agent bubbles, 1,000 files). Fixed three lookups that read the whole table, one of them per recalled hit. The table below is from the same test file on old and new code.

Cloudflare limits (Workers Free, Durable Objects SQLite, https://developers.cloudflare.com/durable-objects/platform/pricing/, page dated Sep 30, 2026): 5 million rows read per day, 100,000 rows written per day, 5 GB stored, for the whole account.

### Fixes

1. `memory.ts` `posOfMessage`: found a message's turn with a join on `BETWEEN`, which read every turn. Now two indexed lookups: the message's seq, then the last turn that starts at or before it. Recall looks up each hit, and edit and delete look up the edited message, so all three dropped.
2. `schema.ts`: index `mem_turns (key)`. A run's end looked up its turn by key with a full scan.
3. `schema.ts`: index `deliveries (at)`. The 30-day sweep deleted by age with a full scan.

Both indexes are new steps at the end of the list. `schema-columns.json` lists them.

### Per-day budget for one active user (estimate)

Assumptions: 200 human messages a day, each with 3 agent bubbles; 200 agent runs a day; 50 chat opens a day; 10 edits, 10 deletes, 10 reactions a day; 20 memory recalls a day; 5 catch-up reads a day. Large-room figures from the table.

- Reads before the fixes: about 1.10 million a day, 22% of the 5 million budget. Recall alone was about 595,000 (54%) of it.
- Reads after the fixes: about 266,000 a day, 5% of the budget.
- Writes after the fixes: about 14,000 a day, 14% of the 100,000 budget.

The biggest remaining read term is the mention scan (up to 500 rows per send, reaction, edit, or delete), then chat opens (one row per file, because the snapshot carries every file).

## Discoveries

- **Test harness counter bug, found and fixed in the harness:** the counter drained cursors every 10,000 statements, and it drained the cursor it had just returned. The caller's `.one()` then saw no rows. The drain now runs before the new cursor is pushed. U90's `room-reads-worker.ts` has the same ordering bug, latent at its smaller statement count. I did not change U90's file.
- **Remaining linear reads, not fixed (follow-ups):**
  - Chat open reads every file row, because `listSpace` puts every file in the snapshot. Changing that changes the client's snapshot contract, so it is a protocol change.
  - Folder stat and list read every file under the folder. A stored folder total would fix stat; list is output-proportional.
  - The memory naps need a working `compress`. This harness does not have one, so the memory tree is never built here. `memory view` therefore reads raw turns (4,107 rows). In production it reads built nodes.
- **Shared `/tmp` is full:** `/tmp` is a 7.9 GB tmpfs. Almost all of it is a 6.9 GB Miniflare directory `miniflare-c4cf4a8abd7a16ed5a14a4d02398688f`, whose UserDO WAL is 7.3 GB and is being written by a live test process from another session (`reminders.test.ts`, a `_land` workerd). I did not touch it. My runs use `TMPDIR=/home/keyur/.cache/u91-tmp`. Another session owns the big file, and it looks like a runaway WAL worth a look.
- **Main moved during the unit:** `63bc70c4` (`heavy.sh` refuses when `/tmp` has under 1 GB free) was merged into this branch. It has no effect on the fixes.
