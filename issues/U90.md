# U90: room reads grow with the burst window and the unread count

## Report

STATUS: done

Production read 79.8M rows in an hour on the RoomDO namespace. The send path read about two rows per message
that sat in the open burst window, and about two rows per unread agent message, on every human send. Both
grew with the room, so a long burst or a chatty agent turned one send into thousands of reads.

### Rows read per human send (workerd, `storage.sql` cursor `rowsRead`)

Measured with `test/room-reads-worker.ts` (a `RoomDO` subclass that wraps `sql.exec`). Blocks of 100 sends,
one socket, no agent. "Before" is the `main` schema and code. "After" is this branch.

| Sends so far (block) | Before | After |
| --- | --- | --- |
| 1-100 | 152.7 | 102.2 |
| 101-200 | 357.0 | 156.0 |
| 901-1000 | 1,957.0 | 156.0 |
| 1001-1100 | 2,158.0 | 157.0 |
| 2901-3000 | 5,958.0 | 157.0 |

With 2,000 unread agent messages in the room (no human read), before the fix a human send read at least
2,500 rows: 2,000 from the unread count and 500 from the mention scan, plus the window scan. After the fix it
reads 661 (500 from the mention scan, the existing `MENTION_SCAN` bound, plus the flat cost). The before figure
is the sum of the per-statement counts, not a separate run.

Bursts that close between blocks show the same flat cost (about 164 a send including the flush) before and
after, so the history itself was not the problem. The open burst window and the unread count were.

### Per-statement cost on the send path (1,000 sends, before the fix)

| Statement | Rows per send | Cause |
| --- | --- | --- |
| `SELECT ... FROM pending WHERE ? OR held_until IS NULL OR held_until <= ? ORDER BY seq LIMIT ?` | 2,101 | `ORDER BY seq` with no index: the plan is `SCAN pending | USE TEMP B-TREE`, reads and sorts the whole window. `warnBusyAgents` runs it on every send. |
| `SELECT count(*) ... FROM messages WHERE ... seq > ? AND kind != 'human'` (chat touch) | 2,000 unread | Counted on every send. Unbounded: grows with unread agent messages. |
| `SELECT ... mentions ... LIMIT 500` (chat touch) | 500 | Bounded by design (`MENTION_SCAN`). Left as is. |

After the fix, the window query reads at most 100 rows a send (`MAX_DELIVERY_ENVELOPES`), the unread count is a
kept meta value, and the rest is a fixed cost of about 60 rows.

### Changes

- `apps/server/src/room/schema.ts`: two steps appended at the end of `ROOM_STEPS`:
  `pending_seq ON pending (seq)` and `pending_held ON pending (held_until, at)`.
  `EXPLAIN QUERY PLAN` moves from `SCAN pending | USE TEMP B-TREE` to `SCAN pending USING INDEX pending_seq`,
  and the start of the window from `pending_at` to `pending_held`.
- `apps/server/src/room/log.ts`: `RoomLog.unread()` returns a kept count in meta `unread`. The first call
  counts the chat. `addMessage` (non-human) adds one, `deleteMessages` subtracts a live non-human message past
  the read mark, and `markRead` subtracts the newly read ones. A chat without a kept count is counted on its next
  read, so no backfill step is needed.
- `apps/server/src/room/chat-touch.ts`: uses `log.unread()` instead of the per-send count.
- `apps/server/test/fixtures/schema-columns.json`: `pending` lists its two new indexes.

### Tests

- `test/room-send-reads.test.ts`: 3,000 human sends in blocks of 100, then 2,000 agent messages, then one more
  block. Asserts no block reads more than 1,000 rows a send. The bound is set above the flat cost (about 160,
  or 661 with 500 unread agents) and below the old cost (5,958 at 3,000 sends).
- `test/room-send-cost.test.ts`: the kept unread count equals a count of the chat after every kind of change
  (human and agent sends, deletes, reads, a read past the log, a read that does not move). It also checks that
  an uncounted chat is counted once and kept. A third test checks, with `EXPLAIN QUERY PLAN` on 3,000 pending
  rows, that the window query uses `pending_seq` with no temp B-tree, and that the window's start uses
  `pending_held`.

### Deviations

- Not run: `bun run check` (the full gate), per STANDING item 9.
- The `unread` count is a kept value in meta rather than a new table. It is exact, so the number shown does
  not change.

### Follow-ups

- `warnBusyAgents` still reads the first 100 window rows on every send, so the send path has a fixed cost of
  about 100 rows once the window is full. Rows beyond that are not read.
- The window query, when the window is all held (a daily-limit hold), still reads the held prefix in seq order
  on every send. Not measured. `EXPLAIN QUERY PLAN` shows the scan, not the cost.
- `mentions` in `chatTouch` reads up to 500 rows a send with 500+ unread agent messages. Bounded by design.
- `signal_window` `count(*)` and `min(at)` read up to 20 rows each per send. Bounded by `MAX_SIGNALS`.
- `chatTouch`'s `react` query scans `events` for the latest agent reaction. `events` is trimmed to about 1,000
  rows, so it is bounded.

## Discoveries

- The per-send `unread` count and the window scan were the only unbounded reads on a human send. Everything
  else is a point lookup, a bounded `LIMIT`, or a table the object trims or caps.
- `EXPLAIN QUERY PLAN` on `bun:sqlite` gives the same plans as on workerd for these queries, so the plan test
  runs in plain `bun test`.
