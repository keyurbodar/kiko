# U56 Account deletion converges: a failed start deletes nothing

**Model** Claude Haiku 5.5 medium. **Wave** 7. **Timebox** 120 min. **Port** 8856.

Source: review C (`issues/review/C.md`) findings C1, C2, C3, C5, and review F finding F01. U11 promised "a failed enqueue rolls back, nothing is half-deleted, the user can retry." The review shows four ways that promise breaks.

## Do

1. **C1, high.** A 503 from a failed enqueue does not stop jobs already queued (a send can fail after the queue accepted part of a chunked batch). Those jobs close and wipe rooms and agents on a live account. Fix: stamp every deletion job with the deletion generation (`beginDeletion` already writes `Date.now()` under `DELETING`). `runDeleteJob` returns at once when the user object's current generation differs or is cleared. `cancelDeletion` clears it, so stale jobs become no-ops. Files: `apps/server/src/jobs/delete-account.ts`, `apps/server/src/user/user-do.ts`. Test: in `apps/server/test/delete-account.test.ts` the fake `enqueue` already queues a partial job (around lines 150-152); run that job through `runDeleteJob` after the abort and assert nothing was deleted. Show it fails today.
2. **C2.** `beginDeletion` wipes the Kernel account (`user-do.ts` ~851-853) before the enqueue, so a rollback cannot undo it. Move `kernel.wipe()` into the final step of `deleteAll`, under the same tombstone. Test with a spy: with `enqueue` throwing, the Kernel wipe is never called.
3. **C3.** In `apps/server/src/auth/account-route.ts` (~79-82) the abort calls `cancelDeletion()` then `restoreUser()`. If the first throws, the D1 tombstone stays and the user is locked out. Restore the user first (a retry's `beginDeletion` overwrites a leftover mark), or make both run regardless. Test: `cancelDeletion` throws once; `deleted_user` is cleared and a second start succeeds.
4. **C5.** `core/durable/src/wipe.ts` `storedRows` returns 0 for any finished wipe, and counts the marker key itself mid-wipe, so the residue probe cannot see rows written after a wipe. Count rows excluding the marker keys and drop the early return. Fix the tests that are true by construction (`wipe-tombstone.test.ts:45`, `wipe-order.test.ts:62` should assert an exact count).
5. **F01, high, AGENTS rule 5.** The dev route `/api/dev/account/<userId>/(residue|rerun)` in `account-route.ts` (~15, 109-149) builds a user stub from the URL id. Take the id from the session, as `seed-agent` already does nearby, and drop the path segment. Update the `account-delete` verify suite to match. Test: session A cannot act on user B.

Only if it deletes code without new risk: review C's Q1 (fold the `DELETING` key into one state in `wipe.ts`; beware the hazard it names: `beginDeletion` must still return the rooms list on retry). If it is not clearly simpler, skip it and say why.

## Acceptance

Each fix has a test that fails on old code; say so with the output line. `bun scripts/check.ts` green after merging `main`. `bun yuki verify account-delete --url http://localhost:8856` passes on your own server.
