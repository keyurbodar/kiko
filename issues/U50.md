# U50 Does the lead judge small versus slow work well, and does "status" disturb the work

**Model** Claude Haiku 5.5 medium. **Wave** 6. **Timebox** 90 min. **Port** 8850.

## Why

The owner's design: the lead does small tasks itself and dispatches anything longer than instant to a background worker (`start_work`), with no budgets or thresholds. A message like "what is the status" must be answered from worker state and must not steer or stop the work. A note like "do it fast" reaches the worker through `steer_work`. The model decides what is small. This unit measures whether the real model does that. It is a spike: no product code changes.

Read first: `apps/server/src/agent/prompt.ts` (`WORK_LINES`), `apps/server/src/agent/extensions/work.ts`, `core/agent/src/workers.ts` (`note()`), `core/agent/src/mid-run.ts`, and the existing suites `apps/cli/src/verify/suites/workers-model.ts` and `mid-run-model.ts`. Reuse their client helpers.

## Do

Write `issues/evidence/u50/spike.ts`, a script that drives the yuki CLI client against your own server (`--url http://localhost:8850`, dev keys from `apps/server/.dev.vars`). Run about 10 everyday requests, each in a fresh chat with the default lead model:

1. rename a file
2. fix one typo in a file
3. answer a factual question from a file already in the chat
4. add a line to three files
5. write a 600 word draft into a file
6. summarize five files into one
7. research a topic on the web and write a short report (needs a worker by design)
8. a multi-file change: restructure a small folder
9. a request that turns out larger than it looks
10. two requests in one burst, one small and one large

For the slow ones (5 to 10), send "what is the status?" a few seconds after the lead starts, then later "one note: keep it short" or "do it fast".

Record per request, from the server's real events and the agent's tool calls (find them through the CLI and the dev stats or room log, not by reading model prose):
- did the lead do the work itself or call `start_work`; how many tool rounds the lead's own run used
- time to the lead's first visible reply, time to done
- for status: time from the status message to the reply; whether the reply named real worker state; whether the worker received any input because of it (it should not); whether the worker kept running
- for the note: did it reach the worker through `steer_work`, and did the outcome follow it
- tokens per request if the dev stats expose them

Run the set twice. Write `issues/evidence/u50/results.md`: one table, the raw numbers, and a plain verdict for each question: does the lead judge small versus slow well; is status answered fast without touching the work; do notes reach the worker. Name each misjudgment with its request and what the lead did. If a fix is needed, say which: prompt wording in `WORK_LINES`, a tool description, or a structural gap. Do not implement it.

## Acceptance

`results.md` with both runs, every number traceable to a log file under `issues/evidence/u50/`. Commit only under `issues/evidence/u50/` and your report in this file.
