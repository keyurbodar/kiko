The per-token write problem was already fixed. `createCoalescingStorage` holds streamed revisions for 2 s. A 4,000-character stream writes about 16 revision rows, not one per token.

Per-day budget for one active user (estimates, not measured end to end):
- Assume 200 messages a day, each with about 10 s of reply. A turn then reads about 290 rows and writes about 195 rows.
- That is about 58,000 reads a day (about 1.2% of the 5,000,000 free daily limit) and about 39,000 writes a day (about 39% of the 100,000 free daily limit).
- The writes are mostly pi-durable's bookkeeping (see below), not yuki's.
- Before the fix, the inbox scan added about one read per inbox row per turn. At 1,400 rows (200 a day for 7 days) that is about 1,400 extra reads per turn, roughly 280,000 a day. The hourly prune added about 1,400 reads an hour. After the fix both are near zero.
- Each outbox reopen read every run the outbox ever ended. That grew without limit.

What the change does:
- The inbox's `envelopeIds` (called at each run end) read every inbox row, because `request_id` had no index. It now uses `inbox_by_request`.
- The inbox's prune read every submitted row, because no index had `at`. It now uses `inbox_by_submitted_at`.
- The outbox's `openRows` read every ended run, because `ended` had no index. It now uses `outbox_by_ended`.
- Cost: each turn writes about 6 more rows, because inserts and updates maintain the new indexes.

FOLLOW-UPS:
- pi-durable owns most writes. For a fresh turn, its top statements write about 24 rows for task inserts, 16 for documents, 10 for record_ids, 6 for durable_metadata, 6 for entries, and 8 for submissions. These are pi-durable's tables; not changed. A longer coalescing window (`intervalMs`, 2 s today) would cut revision writes, but it widens the crash window the coalescing test covers. Needs a decision.
- Outbox rows are never deleted (only `clear()` on reset). The table grows forever. Reads no longer depend on it, but storage does. Deleting ended rows needs care: `INSERT OR IGNORE` on `run_id` relies on the row to stop a replayed run from starting again.
- Workers: `running()` lists the whole workers table. It is small (7-day retention), so it is left as is.
- Not measured: worker steps, memory naps, browser, reminders and routines (user and room objects), and the transcript beyond 20 turns of 2,000 characters (about 30 turns is where a reset happens at 60,000 characters).

## Discoveries
- `inbox.envelopeIds` runs on every run's end, through `heard()`, so the inbox's full history was read once per run.
- Each outbox reopen (after an eviction) reads all ended runs. That is the only per-open cost that grows without bound.
