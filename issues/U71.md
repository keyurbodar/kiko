ROOT CAUSE
- Parallel tool execution is intact. Instrumented run (temporary timing log, reverted): in the single-worker case all 20 `composio_search_web` calls started within 80 ms (20462 to 20547 ms) and the tool span was about 3 s. pi-durable runs every eligible tool task at once (`harness/scheduler.js` #reserve); `toolExecution: "parallel"` is its default, and the repo sets no `executionMode: "sequential"`.
- The failing runs are the talker starting one worker per lookup. Instrumented: calls ran in batches of 3 (`MAX_WORKERS`), and the talker said "Bun is done, starting the next search now". Each worker made one search per model turn: 72 turns (wall 94 s) and 111 turns (wall 80 s, B). The same happened in the two evidence runs: 82 and 113 turns.
- The talker decides this, and WORK_LINES already says "Give a job with many parts to one worker whole ... Do not split it into batches". Nothing in the code forces it. The start_work description said "one clear task", which reads as one worker per lookup. Since 0d9fb327 the Composio tools run only in workers, so the talker cannot make the parallel calls the suite prompt asks for, and it creates workers instead.
- Not the cause: pi-durable parallelism, the Composio limiter (40 at once), and the prompt (only a status line was added after c97ac85b, which measured 17 s with one worker).

DEVIATIONS
- The test checks the tool's description text, not the model's choice. A real choice needs the real model, and the live suite above is the evidence for it. Three post-change runs is a small sample. Pre-change, the split happened in 2 of 5 runs. Some runs fail the 0.6 limit even with one worker, see the follow-up.

FOLLOW-UPS
1. The suite's metric divides the whole turn's wall by the sum of call times. That wall includes model turns. A single-worker run that is fully parallel can still fail: the 0.717 run took 5 turns and 30.5 s for 42.6 s of calls, while its calls ran together. A fair check measures the calls' own span (first start to last end) or their peak concurrency. That needs a server counter, so it is a suite change and was not made here.
2. The suite prompt asks for "all in ONE response as parallel tool calls" of `composio_search_web`. The talker has no such tool since 0d9fb327, so the prompt pushes it toward the split. A suite prompt that asks for one job would match what the product now does. Also not made here.
3. WORK_LINES still says "one clear task". It is consistent with the new description but could say "one whole job". Left unchanged so the prompt cache holds.
