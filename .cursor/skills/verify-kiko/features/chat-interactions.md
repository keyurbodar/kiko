# Chat interactions

Everything a reader can do to a message: open its menu, swipe it to reply, react to it, follow a reply back to what it answers, and see who is typing. The transcript is a conversation, not a document — the same message responds the same way whether the viewer wrote it or the agent did, with one exception the menu makes visible.

## Sub-features

- `menu-right-click` — right-clicking any message opens a menu; the viewer's and the agent's menus list the same actions except that only the viewer's carries `edit`.
- `swipe-to-reply` — dragging a bubble sideways past its threshold arms a reply and the bubble snaps back; a vertical drag scrolls instead and never fires.
- `reactions-toggle` — a message carries **one chip per emoji**, never one reaction overall. Each chip is toggled on its own, so reacting with a second emoji ADDS a chip rather than replacing the first, and a message several people have reacted to shows one chip per emoji with its own count. The viewer is at most one reactor on any chip: the chip they are on carries `aria-pressed="true"` and takes the `--user-bubble` fill and the `--user-bubble-text` colour, and their toggling never moves anyone else's chip.
- `reaction-badge` — one 28px circle per emoji, inside a positioned row that sits outside the bubble's corner, drawn with a shadow ring rather than a border.
- `reply-quote` — a reply's quote is the first child of its bubble: the sender's label clamps to one line, the quoted text to two, and the text is cut on a grapheme boundary.
- `reply-quote-thumb` — a quote whose parent is an image carries a 32px thumbnail beside the text, and only that quote lays out as a row.
- `reply-jump` — clicking the quote scrolls the transcript to the message it answers.
- `unread-rule` — a rule sits before the first unread incoming message, is never the last row, and collapses out of the layout when it retires.
- `picker-search` — the picker replaces the menu's quick strip and actions when opened, seeds its footer from the first cell so the preview is populated immediately, and filters the grid as you type. It is preloaded when the menu opens, so it appears at once.
- `typing-bubble` — typing renders as an in-list bubble of three dots with no avatar and no visible label; the label is announced to screen readers instead.

## How to get to it (user POV)

- Right-click any message, yours or the agent's, to open its menu.
- Drag a bubble away from the other side of the conversation, then release, to reply to it.
- Click a reaction badge to add or remove your own reaction.
- Click the quoted block at the top of a reply to jump back to the message it answers.
- Pick a reaction from the menu to open the emoji picker, and type in its search field to filter.
- Send a message to watch the typing bubble appear for whoever is replying, and the unread rule retire.

- **Swipe fires past its threshold, in EITHER direction, on either side.** Observe: a drag that crosses the axis lock past 48px arms a reply; a shorter one leaves no trace.
  - Load `today`, read a row's centre with `page.evaluate(() => { const r = document.querySelector('[data-component="chat-row"]'); const b = r.querySelector('[data-slot="bubble"]').getBoundingClientRect(); return { x: b.left + b.width / 2, y: b.top + b.height / 2 }; })`. Drag **either way** — direction belongs to the reader, not the sender. There is no wrong way to swipe, because nothing on screen would tell the reader which way a given row is allowed to move.
  - The indicator's edge **follows the drag**: rightward sets `data-swipe-side="start"` and hangs the indicator at `left: 16px`, leftward sets `data-swipe-side="end"` at `right: 16px`. An earlier design gated each side to one direction, so a leftward swipe on the agent's row was silently dropped and the gesture read as dead.
  - **Two input paths, one machine.** A pointer drag and a trackpad two-finger swipe both work. The trackpad path is `wheel`-driven — two fingers deliver `deltaX`, and the row is only ever hovered, so a pointer-only gesture is unusable on a laptop. Drive it with `page.evaluate` dispatching `new WheelEvent("wheel", { deltaX: -40, deltaY: 0, bubbles: true, cancelable: true })` repeatedly at the swipe row; the delta is scaled by `0.25` and the gesture ends on a 75ms wheel silence. **Allow ~2s before reading the commit** — the snap-back is a `requestAnimationFrame` spring, and a probe context that throttles rAF finishes it far later than a focused browser.
  - A vertical-dominant `wheel` (`|deltaX| <= |deltaY|`) must never engage: it is the transcript scrolling.
  - **`page.mouse` drives the gesture fine — that was once misread as broken.** A `page.mouse.move` / `down` / several `move` / `up` sequence writes `--swipe-x: 64px` onto `[data-component=chat-swipe-row]`, sets `data-swiping="true"`, and commits a reply on release. Read the state with `page.evaluate(() => { const row = document.querySelector('[data-component=chat-swipe-row]'); const i = row.querySelector('[data-component=chat-swipe-indicator]'); return { swiping: row.hasAttribute("data-swiping"), side: row.getAttribute("data-swipe-side"), swipeX: row.style.getPropertyValue("--swipe-x"), indicator: i ? getComputedStyle(i).display : null }; })` — `--swipe-x` is written as an inline custom property, so read it there rather than off the rendered transform.

  - `probe().unreadRule` reflects the mounted DOM, and a rule outside the virtualized window legitimately is not mounted. Write the position to `/tmp/kiko-verify-evidence/unread-rule.json`.

- **The unread rule retires when the viewer sends.** Observe: after the viewer sends, the rule collapses out of the layout and every message reads as read.
  - **Pending — no send path exists.** The harness exposes `setState`, `setTyping`, `setReplyTarget`, `openMenu` and `openPicker`; none of them sends a message, and the composer is not mounted in the chat surface, so no user path retires the rule. This recipe cannot run until a send path lands.
  - When it does, the retirement is a layout collapse rather than a fade: `[data-retiring]` on the slot flips `grid-rows-[1fr]` to `grid-rows-[0fr]` — the `data-[retiring]:grid-rows-[0fr]` utility in `apps/web-solid/src/chat/ui/UnreadRule.tsx` — and the clip box's `overflow-hidden` clips the rest. - **The picker takes the menu over, seeds its footer, and filters as you type.** Observe: opening it leaves no quick strip and no actions behind, its footer is populated the instant it appears, and typing narrows the grid.

## Gotchas

- **Menus and pickers portal out of the column.** Scope them by `[data-component="chat-menu"]` and `[data-component="chat-emoji-picker"]`, never by a bubble or column ancestor. A portalled menu is also a common source of a stray non-zero `transition-duration`; the no-animation probe in [Chat bubbles](./chat-bubbles.md) must include it.
- **The menu's own trigger is not a thing to click.** `.chat-menu__trigger` is a zero-size `position: fixed` anchor — a class plus an inline style in `apps/web-solid/src/chat/ui/MessageMenu.tsx` — that only receives a replayed `contextmenu` event so Kobalte's positioning has something to anchor to. It is never visible and never hittable; asserting anything about it, or trying to click it, is a dead end. Drive the menu with `openMenu` or a real right-click on a row.
- **The menu's quick strip is buttons, not menu items.** `[role="menuitem"]` misses the five emoji buttons, so a recipe that counts menu items undercounts by five. Read the emoji strip and the action list separately, as the recipe does.
- **`openMenu` and `openPicker` return whether a dialog actually opened.** Read the return value and `probe().overlay`. A `false` with a previous overlay still in the document is a no-op, not an open menu, and the DOM read alone will happily return the stale one.
- **The swipe works in both directions, on both sides.** Direction belongs to the reader: a rightward drag sets `data-swipe-side="start"` (indicator at the left edge) and a leftward one sets `"end"`. An earlier design tied the direction to the sender, so a leftward swipe on the agent's row was silently dropped — that is now a defect, not the contract.
- **The swipe indicator only paints past the axis lock.** `[data-swiping]` gates it with `display: none`, so a tap correctly leaves no trace. An indicator visible on a tap means the lock is not deciding the axis, which is the defect the vertical-drag recipe exists to catch.
- **`SwipeToReply` must pass `ref` and the two data attributes EXPLICITLY, never spread them.** `apps/web-solid/src/chat/ui/SwipeToReply.tsx` writes `ref={swipe.handlers.ref}`, `data-swiping={swipe.handlers["data-swiping"]}` and `data-swipe-side={swipe.handlers["data-swipe-side"]}` one by one. **Do not "simplify" that back to `{...swipe.handlers}`** — it silently breaks the gesture two different ways. Spreading reads the getters *once* at spread time, so `data-swiping` freezes at its initial value and never marks the row mid-drag; and a `ref` that arrives through a spread is not a ref at all in Solid, so the gesture never receives its element and the swipe does nothing. A broken `ref` fails silently — there is no error, the row just never moves.
- **`page.mouse` DOES drive the swipe.** A `page.mouse.move` / `down` / several `move` / `up` sequence writes `--swipe-x` onto `[data-component="chat-swipe-row"]`, sets `data-swiping="true"`, and commits a reply on release. An earlier version of this file claimed it produced neither and told the reader to synthesise PointerEvents — that conclusion came from a bug, not the driver (see the recipe above), and a recipe that hand-rolls `PointerEvent`s is now unnecessary work that hides the real failure. Read `--swipe-x` off the row's inline style and `data-swiping` off the attribute, not the rendered transform.
- **The typing label is in the DOM but not on screen.** It lives in an `.sr-only` span inside the typing row, so any assertion based on `textContent` alone reports a visible label that is not there. Walk the text nodes and exclude `.sr-only`, or assert the row's rendered geometry instead.
- **The radii in this file are on the `--brm` idiom, unlike the transcript's.** The menu's 20px, the picker's 16px, its search 10px, its cell 8px and the typing bubble's 18px are all `calc(Npx * var(--brm))` utilities, matching kat's reference stylesheets, while the transcript's own radii are literals. On a browser without `corner-shape: squircle` these read half. **A halved corner here is the token system working — do not report it as drift and do not "fix" it.** The one worth knowing is the typing bubble: it asks for the same 18px as `[data-slot="bubble-content"]` but through the idiom, so it reads a few pixels rounder than the message bubbles beside it. That gap is known and owned; read it against the token.
- **There is one reaction per message, so "a count that only grows" is the wrong failure to look for.** The old failure was a toggle that added instead of replacing across a cluster. Now the real failures are a *second* badge appearing on a message that already has one, and a swap that adds rather than replaces. Toggle the same badge twice and compare all three readings each time, and separately pick a *different* emoji and assert the badge count stays at `1` with a new `data-emoji`.
- **The quote clamps to two lines, not one.** The sender's label is a one-line ellipsis and the quoted text is a two-line clamp. An assertion written from either alone will fail against a correct quote, so read both in one pass.
- **`bun test` resolves `solid-js` to its server build**, where `createMemo` never re-runs. A unit test that derives state with `createMemo` will pass on a stale value and prove nothing. Anything derived belongs in these browser recipes, not in a `bun test`.
- **Geometry measured in a fallback face is not a measurement.** Nothing here depends on a font beyond the token layer, but wait for the fonts before reading sizes — see [Kat token layer](./kat-tokens.md).
